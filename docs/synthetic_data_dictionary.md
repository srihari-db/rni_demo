# Synthetic Data Dictionary — RNI Intelligent Operations Command Center

> **All data is synthetic.** Customers, products, manufacturers, quantities, prices and costs are fictional and
> exist only to demonstrate analytics patterns to FFF Enterprises. There is no PHI, no patient identity, and no
> real clinical record. `dosing_rules` contains *simulated stocking-policy metadata*, never patient dosing.

## 1. How the data is produced

`scripts/generate_rni_data.py` runs a **deterministic RNI operations simulator** (`src/data/simulator.py`). It
doesn't draw independent random rows per table. It simulates operations day by day, in chronological order:

1. **Masters first.** It creates 15 customer locations, 30 products, 34 RNI devices, 203 customer/SKU assignments,
   PAR / mandatory-minimum policies and stocking-policy rules.
2. **24 months of demand** (2024-11-01 → 2026-10-30), one profile per customer/SKU:
   - *Regular:* Poisson with weekday effect and trend.
   - *Seasonal:* winter respiratory peak.
   - *Intermittent:* Bernoulli events with geometric sizes.
   - *Emergency:* rare bursts, with a summer boost for antivenoms.
3. **Weekly replenishment reviews.** These simulate the manual Excel decision: `(PAR − position) × site ordering
   bias × noise`. With a site-specific probability, the request is intentionally inflated 1.8–4× (**excessive
   allocations**; ground truth in `shipment_orders.synthetic_excess_flag`). A simulated FFF review then approves,
   modifies, rejects or partially fills the request. SAP shipment, then receipt after the regional lead time.
4. **Lot-level inventory:**
   - Lots are manufactured monthly per SKU.
   - The distribution center picks lots FEFO with a minimum remaining shelf life, so short-dated stock occurs
     naturally.
   - Sites consume FEFO.
   - Expired lots are disposed.
   - Every movement is written to the **event ledger**.
5. **Returns.** A monthly return review returns excess stock above 1.4 × PAR, and short-dated surplus, **only from
   lots physically on hand and unexpired**. Each return carries a synthetic cold-chain shipping cost and a QA
   processing cost.
6. **Executive scenarios** (`config/demo_scenarios.yaml`) are staged *inside* the same ledger: at the start of each
   scenario window an anchor shipment or return is booked, and demand in the window is scripted. Ledger
   reconciliation therefore still holds.
7. **IoT telemetry.** 30 days at 15-minute intervals for every fridge and freezer. One planted compressor-vibration
   drift on `RNI-DEV-0701`.

**Forecasts and recommendations are not generated by the simulator.** `scripts/run_forecasting.py` executes the
forecasting pipeline (MLflow-tracked), and `scripts/run_recommendations.py` executes the decision engine. Financial
KPIs are derived by SQL in `sql/create_gold_views.sql`.

**Reproducibility.** The fixed seed is `20261030`, and every entity gets its own RNG keyed by stable IDs, so adding
an entity doesn't reshuffle the others. Regeneration is byte-identical within the pinned job environment. A
different NumPy version may change a few random draws, but all staged scenarios are scripted and come out exactly
the same everywhere.

### Identifier formats (stable across the dataset)

| Entity | Format | Example |
|---|---|---|
| Customer | `CUST-NNN` | `CUST-001` = Desert Crest Medical Center ("Hospital A" in the brief) |
| Product / SKU | `SKU-NNNN` | `SKU-1001` = Hyperimmune Globulin 1,500 IU ("Product A" in the brief) |
| Device | `RNI-DEV-CCNN` | `RNI-DEV-0101` |
| Lot | `L<sku4>-<yymm><A-Z>`, scenario lots end in `X` | `L1017-2502X` |

| Return | `RT-<yymmdd>-<cust>-nn` | `RT-260601-005-01` |
| Ledger event | `EV-<8 digits>` (chronological) | `EV-00000001` |

### Key metric definitions

| Metric | Definition |
|---|---|
| Inventory value | `on_hand_qty × unit_cost` (synthetic) |
| Near-expiry | units in lots expiring ≤ 90 days after the as-of date |
| Excess above PAR | `LEAST(on_hand − near_expiry, GREATEST(0, on_hand − PAR))` — exclusive of near-expiry |
| Healthy | `on_hand − near_expiry − excess` |
| Pending request exposure | `(requested − recommended)⁺ × unit_cost` for pending requests |
| Potential excess exposure | excess above PAR + pending request exposure (non-overlapping) — **potential, not savings** |
| Est. avoidable logistics | 12-month shipping + processing cost of returns with reason EXCESS_STOCK / STOCK_ROTATION |
| Return rate | returned units ÷ shipped units, same period |
